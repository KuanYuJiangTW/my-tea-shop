# 設計文件：製茶過程頁多茶款擴充

> 2026-07-25 修訂：依店主回覆更正三處——蜜香紅茶為**球形紅茶**（非條型）、製程參數採方案 B（不寫溫度時間）、四季春與紅烏龍為**合作茶農**產品。修訂前的條型紅茶假設已作廢。

## 0. 核心洞察：差別，全在中間那幾步

五款茶的製程**前段完全相同、後段完全相同，只有中間分道揚鑣**。這不是為了設計方便而做的簡化，是店主實際做法的忠實結構：

```
共通前段                    分歧段                      共通後段
採摘                    ┌─ 烏龍三款：炒菁 → 揉捻 ─┐    布球團揉
日光萎凋   ─────────────┼─ 蜜香紅茶：揉捻 → 發酵 ─┼───→ 焙火
室內萎凋                └─ 紅烏龍：發酵→炒菁→揉捻 ┘    揀枝包裝
浪菁
```

**這是整頁的頭條，也是資訊架構的骨架。**使用者只要理解「中間那幾步」，就掌握了五款茶的全部差異。

其中最鋒利的一刀是**炒菁的有無**：炒菁用高溫讓酵素失去活性、把氧化按下暫停鍵。烏龍要停在半路（所以炒菁），紅茶要走到底（所以不炒菁）。這一格被劃掉的瞬間，就是本頁的記憶點。

而**布球團揉是五款茶共通的**——這是本店的識別：連紅茶都做成球形，而市面上的紅茶絕大多數是條型。

## 1. 內容模型

### 1.1 三個製法家族

分類依據是**分歧段的走法**，不是品種或行銷分類。

| 家族 key | 名稱 | 成員 | 分歧段走法 |
|---|---|---|---|
| `partialBall` | 部分發酵球形烏龍 | 高山烏龍、金萱、四季春 | 炒菁 → 揉捻 |
| `fullBall` | 全發酵球形紅茶 | 蜜香紅茶 | 揉捻 → 發酵（**不炒菁**） |
| `heavyBall` | 重發酵球形烏龍 | 紅烏龍 | 重發酵 → 炒菁 → 揉捻 |

三個家族的共同點是**都以布球團揉成球形**，故 key 皆以 `Ball` 結尾。

> 為什麼不用氧化度當分類軸：氧化度是連續光譜，切不出「炒菁存不存在」這個離散的工序分歧，而後者才是使用者看得到、記得住、也真正決定茶種歸屬的差異。

### 1.2 工序序列（依茶款）

**編號採每款茶自己的順序（01..N）**，不使用跨茶款的固定槽位——因為分歧段的工序順序本身就因茶而異（紅茶先揉捻後發酵，紅烏龍先發酵後炒菁），硬套固定槽位會扭曲事實。

| 段落 | 工序 key | 烏龍三款 | 蜜香紅茶 | 紅烏龍 |
|---|---|---|---|---|
| 共通前段 | `pick` 採摘 | 01 | 01 **強化**（著蜒芽葉） | 01 |
| | `witherSun` 日光萎凋 | 02 | 02 | 02 |
| | `witherIndoor` 室內萎凋 | 03 | 03 | 03 **強化**（長時） |
| | `shake` 浪菁 | 04 | 04 | 04 **強化**（重攪拌） |
| **分歧段** | `ferment` 發酵 | — **跳過** | 06 **特有**（第二天） | 05 **特有**（重發酵） |
| | `fix` 炒菁 | 05 | — **跳過** | 06 |
| | `roll` 揉捻 | 06 | 05 **強化**（第二天，先於發酵） | 07 |
| 共通後段 | `ballRoll` 布球團揉 | 07 | 07 | 08 |
| | `roast` 焙火 | 08 | 08 **待確認** | 09 **強化**（重焙） |
| | `sort` 揀枝包裝 | 09 | 09 | 10 |

相對現況的變動：新增 `ferment`（發酵）與 `ballRoll`（布球團揉）兩個 key；**現有 8 個 step key 全部沿用，既有 i18n 文案不作廢**。

三態定義：

- **共通**（`common`）：此茶有這一步，用共通描述
- **強化／特有**（`accent`）：此茶在這一步有專屬做法，顯示專屬文案並加視覺強調
- **跳過**（`skipped`）：此茶沒有這一步，卡片**保留但降階顯示**（劃線／低透明度），且必須給出原因

> `skipped` 保留卡片而非隱藏，是本設計的核心。隱藏＝使用者不知道少了什麼；保留並說明＝製造對比記憶點。`skipped` 卡片只在**分歧段**出現（共通前後段沒有任何茶跳步）。

### 1.4 工藝取捨（專業感的來源）

每款茶一則「為什麼要這樣做」。**內容待店主校對（tasks 0.4）**，方向：

- **蜜香紅茶**：第一天當烏龍做、第二天當紅茶做，最後又回到烏龍的布球團揉——它是三種工法接起來的茶。而蜜香來自小綠葉蟬叮咬後茶樹的防禦反應（著蜒），**要蜜香就不能用藥**，蟲害在此是必要條件
- **金萱**：乳香是品種自帶的揮發性成分，焙火一重就蓋掉 → 所以金萱是五款裡焙得最輕的
- **紅烏龍**：重發酵之後**仍然炒菁**，是它與紅茶的分水嶺——把氧化按下暫停鍵，保住烏龍的甘韻
- **高山烏龍**：高海拔雲霧多、濕度高，日光萎凋看天走，不是照表操課
- **四季春**：品種早生、一年可採多次，是它價格親民的結構性原因（非品質妥協）

### 1.5 產地誠實標示（合作茶農）

四季春（南投名間松柏嶺）與紅烏龍（台東鹿野）為**同輩茶農以合作方式供應**，非自家製作。全站既有文案強調「自產自銷」，若製程頁以「我們的師傅這樣做」一體敘述，對這兩款不成立。

**設計立場：主動標示，並把它寫成優勢而非免責聲明。**

理由是這兩個產地並非隨意選擇，而是各自茶類的原產地——名間松柏嶺是台灣四季春主產區，鹿野是紅烏龍的發源地。因此敘事定調為**「每一款茶，都選它的原產地」**，而非「自家做不完所以外調」。

實作要求：

- 每款茶顯示**來源徽章**：`自家茶園．阿里山梅山` ／ `合作茶農．南投名間松柏嶺`
- 合作款的製程敘述改用產地口吻（「松柏嶺的做法」），與自家三款的第一人稱區隔
- 徽章為中性資訊樣式（非警示色），與其他規格標籤同級
- 此標示同時降低產地標示不實的合規風險——主動揭露即無爭議

### 2.1 分歧段的視覺處理

分歧段是本頁的重點，需與共通段明顯區隔：

- 共通前／後段：白底卡片，一般樣式
- 分歧段：**整段加底色容器**（`bg-tea-green-mist`）並加標題「這裡，五款茶分道揚鑣」
- 分歧段內的 `skipped` 卡片：劃線 + `opacity-50`，並顯示 `skipReason`
- 切換茶款時，**只有分歧段的內容變動**，共通段保持不動——強化「差別只在這裡」的認知

### 2.2 兩層 sticky 的處理

現況已有一層 sticky 步驟導覽（`ProcessContent.tsx:138`，動態同步 header 底部）。再加一層茶款選擇器會吃掉手機過多垂直空間。

**決定**：茶款選擇器與步驟導覽**合併為單一 sticky 容器**，上排茶款（5 顆）、下排工序。工序列於窄螢幕改為橫向捲動（`overflow-x-auto`），不用現行 `grid-cols-4` 兩排（工序數已增至 9–10，grid 會變三排過高）。

現有的 `stepBarRef` top 同步與 `IntersectionObserver` 捲動高亮（`ProcessContent.tsx:56-117`）整段保留，只換內容不重寫機制。

### 2.3 切換茶款時的動效

- 分歧段卡片以 `transition-all duration-300` 做狀態轉場，**不整段 unmount/remount**——要讓使用者看見「炒菁那格被劃掉」的過程，這是設計意圖所在
- 切換後捲動位置維持不變（不自動回頂），使用者可停在分歧段比較不同茶
- `prefers-reduced-motion: reduce` 時停用轉場

## 4. 資料結構

新增 `src/data/tea-process.ts`，把「哪款茶走哪條路徑」從 JSX 抽離為資料，避免 5×10 的條件判斷散在元件裡：

```ts
export type StepState = "common" | "accent" | "skipped";
export type TeaKey    = "oolong" | "jinxuan" | "sijichun" | "black" | "redOolong";
export type FamilyKey = "partialBall" | "fullBall" | "heavyBall";
export type Sourcing  = "own" | "partner";

export interface TeaProcess {
  key: TeaKey;
  family: FamilyKey;
  productId: number;              // 對應 src/data/products.ts，供 CTA 導流
  sourcing: Sourcing;             // 自家茶園 / 合作茶農
  divergence: StepKey[];          // 分歧段的實際順序（因茶而異）
  skipped: StepKey[];             // 分歧段中跳過的工序
  accents: StepKey[];             // 有專屬做法的工序
}
```

共通前後段的順序寫成模組常數（所有茶共用），**只有分歧段是 per-tea 資料**——資料結構直接反映第 0 節的洞察。

文案一律走 i18n，此檔只存結構與關聯。i18n key 命名：

- 共通工序文案：沿用現有 `process.steps.<stepKey>.{name,desc,detail}`
- 茶款專屬文案：`process.teaSteps.<teaKey>.<stepKey>.{desc,detail}`（僅 `accent` 需要）
- 跳過原因：`process.teaSteps.<teaKey>.<stepKey>.skipReason`
- 家族：`process.families.<familyKey>.{name,desc}`
- 分歧段標題與說明：`process.divergence.*`
- 來源徽章：`process.sourcing.{own,partner}`
- 對照表：`process.matrix.*`

`zh.json` 與 `en.json` 必須完全對稱（現況已對稱，47 個葉節點，不可退化）。

## 5. 結構化資料

每款茶輸出一份 `HowTo`（`schema.org/HowTo`），`step` **依該茶的實際順序**排列，`skipped` 工序不進 JSON-LD——結構化資料描述的是真實作法，不是教學對比。

- 序列化一律經 `src/lib/seo.ts` 的 `jsonLdString()`（既有慣例，防 `</script>` 突破）
- metadata 沿用 `langAlternates("/process")`
- `HowTo.name` 依 locale 對應中英，與 `products.ts` 的 `name`／`nameEn` 一致
- 每款茶區段加 `id` anchor（如 `/process#black`），讓 AI 可引用到段落層級

## 6. 明確不做的事（scope 邊界）

- **不改** `/products` 的商品價格（惟四季春產地字串需更正為松柏嶺）
- **不新增**綠茶、白茶等未販售茶類的內容
- **不做**製茶影片／動畫插圖（需素材，另案）
- **不動** `experienceCta` 區塊的現有行為
- **不寫**任何溫度、時間、發酵百分比（決策 ① 採方案 B）
- **不做** `/process/[tea]` 子頁（決策 ③ 採階段一，理由見 proposal）

## 7. 驗證方式

本頁不碰高風險區（無金流、庫存、auth、RLS、cron），但仍須：

1. `npm run test` 全綠（既有 26 檔／316 測試不得退化）
2. `npm run lint` 無新增錯誤（`git stash` 前後對比）
3. `npm run build` 成功
4. i18n 對稱性用**程式**比對 `zh.json`／`en.json` 的 `process` 子樹 key 集合，非肉眼
5. `checker` agent 獨立驗收（依 tasks.md 驗收條件逐條查證）
6. **製程正確性由店主校對**（tasks 0.4）——這是唯一無法用程式驗證的部分
