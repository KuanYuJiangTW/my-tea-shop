# 設計文件：製茶過程頁多茶款擴充

> 2026-07-25 修訂：依店主回覆更正三處——蜜香紅茶為**球形紅茶**（非條型）、製程參數採方案 B（不寫溫度時間）、四季春與紅烏龍為**合作茶農**產品。修訂前的條型紅茶假設已作廢。

## 0. 核心洞察：炒菁擺在哪裡，決定了這是什麼茶

五款茶的製程**前段完全相同、後段幾乎完全相同，只有中間分道揚鑣**。而分歧段的差異，可以進一步收斂成一件事——**炒菁的位置**：

```
共通前段          分歧段：炒菁擺在哪裡？         共通後段
（茶廠．第一天）                            （茶廠 → 家）

採摘          ┌─ 烏龍三款：炒菁 → 揉捻 ───┐   初乾（甲種乾燥機）
日光萎凋  ────┼─ 蜜香紅茶：揉捻 → 發酵 ───┼─→ 布球團揉（擠壓機）
室內萎凋      └─ 紅烏龍：揉捻→發酵→炒菁 ─┘   乾燥・揀枝（粗選機／鼓風機）
浪菁                                          焙火（條件性．回家後）
                                              包裝
```

炒菁是用高溫讓酵素失去活性、把氧化按下暫停鍵的一步。所以：

| 炒菁的位置 | 結果 | 茶種 |
|---|---|---|
| **最前面** | 氧化還沒真正開始就按下暫停 | 烏龍（高山烏龍／金萱／四季春） |
| **沒有** | 讓氧化一路走到底 | 紅茶（蜜香紅茶） |
| **最後面** | 讓氧化跑一段，再踩煞車 | 紅烏龍 |

**這是整頁的頭條。**它把炒菁從「一個步驟」升格為「決定茶種的那個開關」，而且完全是店主實際做法的忠實結構，不是為了說故事而簡化。

由此浮現的第二個記憶點：**紅烏龍走的是紅茶的路，只是最後多踩一腳煞車**——它的分歧段前兩步（揉捻→發酵）與蜜香紅茶**完全相同**，差別只在末端補一道炒菁。這讓「紅烏龍到底是紅茶還是烏龍」這個常見疑問有了乾淨的答案。

而**布球團揉是五款茶共通的**——這是本店的識別：連紅茶都做成球形，而市面上的紅茶絕大多數是條型。

使用者不必記 11 個步驟，只要記「**4 + 2~3 + 4~5**」，再加上「炒菁擺哪裡」這一句。

### 0.1 兩個必須寫進頁面的細節

這兩件事是本頁與內容農場的分界線，**不可在文案階段被稀釋掉**：

1. **設備名稱**：甲種乾燥機、擠壓機、布球揉捻、箱型焙茶機。真正做茶的人會講機器的名字，寫「使用專業設備」等於什麼都沒說。設備名稱不是製程參數（決策 ① 方案 B 限制的是溫度與時數），可以寫且應該寫。
2. **「回家後自己焙」**：焙火是在自家用箱型焙茶機做的，由店主親手調整風味。全站宣稱的「職人親手把關」在這裡有了具體的落點——初製在茶廠、精製在家，這是台灣茶初製／精製分工的真實樣貌，也是一個有溫度的敘事節點。

## 1. 內容模型

### 1.1 三個製法家族

分類依據是**分歧段的走法**，不是品種或行銷分類。

| 家族 key | 名稱 | 成員 | 分歧段走法 | 炒菁位置 |
|---|---|---|---|---|
| `partialBall` | 部分發酵球形烏龍 | 高山烏龍、金萱、四季春 | 炒菁 → 揉捻 | 最前 |
| `fullBall` | 全發酵球形紅茶 | 蜜香紅茶 | 揉捻 → 發酵 | 無 |
| `heavyBall` | 重發酵球形烏龍 | 紅烏龍 | 揉捻 → 發酵 → 炒菁 | 最後 |

三個家族的共同點是**都以布球團揉成球形**，故 key 皆以 `Ball` 結尾。

`fullBall` 與 `heavyBall` 的分歧段前兩步完全相同，差別僅在 `heavyBall` 末端多一道炒菁——這是頁面必須明講的關係，不可讓兩者看起來像無關的兩條路。

> 為什麼不用氧化度當分類軸：氧化度是連續光譜，切不出「炒菁存不存在」這個離散的工序分歧，而後者才是使用者看得到、記得住、也真正決定茶種歸屬的差異。

### 1.2 工序序列（依茶款）

**編號採每款茶自己的順序（01..N）**，不使用跨茶款的固定槽位——因為分歧段的工序順序本身就因茶而異（紅茶先揉捻後發酵，紅烏龍先發酵後炒菁），硬套固定槽位會扭曲事實。

| 段落 | 工序 key | 高山烏龍 | 金萱 | 四季春 | 蜜香紅茶 | 紅烏龍 |
|---|---|---|---|---|---|---|
| 共通前段 | `pick` 採摘 | 01 | 01 | 01 | 01 **強化**（著蜒） | 01 |
| | `witherSun` 日光萎凋 | 02 | 02 | 02 | 02 | 02 |
| | `witherIndoor` 室內萎凋 | 03 | 03 | 03 | 03 | 03 **強化**（長時） |
| | `shake` 浪菁 | 04 | 04 | 04 | 04 | 04 **強化**（重攪拌） |
| **分歧段** | `fix` 炒菁 | **05** | **05** | **05** | — **跳過** | **07** |
| | `roll` 揉捻 | 06 | 06 | 06 | **05** | **05** |
| | `ferment` 發酵 | — **跳過** | — **跳過** | — **跳過** | **06 特有** | **06 特有**（重） |
| 共通後段 | `dryFirst` 初乾 | 07 | 07 | 07 | 07 | 08 |
| | `ballRoll` 布球團揉 | 08 | 08 | 08 | 08 | 09 |
| | `dryFinal` 乾燥・揀枝 | 09 | 09 | 09 | 09 | 10 |
| | `roast` 焙火 | 10 **選配**（預設淺焙） | 10（淺焙） | — **跳過** | 10（淺焙） | 11 **強化**（重焙） |
| | `pack` 包裝 | 11 | 11 | 10 | 11 | 12 |

**分歧段是全表唯一的差異來源**，請對照 0 節的炒菁位置表閱讀：烏龍三款炒菁在 05（最前）、蜜香紅茶無炒菁、紅烏龍炒菁在 07（最後）。蜜香紅茶與紅烏龍的 05／06 兩格**完全相同**。

相對現況的變動：新增 `ferment`（發酵）、`dryFirst`（初乾）、`ballRoll`（布球團揉）、`dryFinal`（乾燥・揀枝）、`pack`（包裝）五個 key；現有 7 個 step key 沿用，**僅 `sort` 需拆解**（見 1.2.3）。

### 1.2.3 `sort`（揀選包裝）必須拆成兩步

現況 `steps.sort` 把揀枝與包裝寫成同一個最後步驟，與實際流程不符。實際上：

- **揀枝在乾燥時同步進行**（布球團揉之後），枝太長用**粗選機**選枝，一般茶用**鼓風機**篩掉雜物與不良葉
- **焙火完成、風味到位後直接包裝**，不會焙完再回頭揀枝

因此 `sort` 拆為：揀枝併入 `dryFinal`（該步更名為「乾燥・揀枝」），包裝獨立為 `pack` 置於 `roast` 之後。

> **既有文案與實情不符（已於 2026-07-25 經店主確認）**：現有 `steps.sort` 文案寫「成茶後由師傅逐一**手工**揀除老葉、茶梗與雜質」，但實際作法就是粗選機與鼓風機，**無手工揀除**。此為線上營運中頁面的不實工藝宣稱，本次改寫必須修正，不得沿用。
>
> 改寫方向：具名機器反而更強——「枝太長的用粗選機選出來，一般的用鼓風機把雜物和不好的葉子吹掉」比「師傅逐一手工揀除」具體、可驗證，也不必擔心被追問。

### 1.2.1 為什麼「擠壓」不獨立成一步

擠壓（束包機）是在布球團揉階段內反覆使用的**設備**，不是一道獨立工序——束包 → 揉捻 → 解塊 → 再束包是同一個循環。且各茶廠設備配置不同，把它抬成工序會讓流程看起來像本場專屬，實際上並非如此。

**決定**：步驟名稱用業界通用語「布球團揉」，`ballRoll` 一個 key；擠壓機寫在該步的**內文設備說明**中，不進導覽列。

此決定同時確立一條通則：**工序是「做什麼」，設備是「用什麼做」，兩者不同層級。**設備名稱（甲種乾燥機、擠壓機、布球揉捻、箱型焙茶機）一律寫進內文——這是 0.1 節的可信度來源——但不佔工序層級。

### 1.2.2 焙火：條件性工序，也是本頁最有價值的一段

焙火在本店並非每款茶都做，程度也不同：

| 茶款 | 焙火 | 狀態 |
|---|---|---|
| 高山烏龍 | 看客人決定，焙與不焙都有；**網站販售預設淺焙**，唯生茶特別出色的批次才不焙 | `optional` |
| 金萱 | 淺焙 | `common` |
| 四季春 | **不焙**，直接以生茶販售 | `skipped` |
| 蜜香紅茶 | 淺焙 | `common` |
| 紅烏龍 | **重焙** | `accent` |

因此三態不足以描述焙火，需第四態 `optional`（選配）。

**判斷依據（本頁最能顯功力的一段文案，方向如下）**：

> 焙不焙、焙多重，看兩件事：這批茶當下的風味狀態，以及客人要什麼。
> 焙火可以調整風味——讓茶更甜、更厚實，品質也更穩定，把一批茶的短處補起來。
> 但焙過頭，花香和鮮度就沒了。所以只能**適當**焙火。
> 不焙的客人要的是相反的東西：新鮮、清香、花果香。而通常只有青茶類（烏龍）才可能不焙。
> 每一次做出來的茶，風味都有差別——焙火是我們因應客人客製化風味的最後一次調整。

這段之所以重要，有三個理由：

1. **它是真的取捨，不是行銷話術**。焙火有得有失（得甜厚穩定、失花香鮮度），承認代價的敘述遠比「精心焙製」可信
2. **它把焙火從工序變成對話**——「因應客人客製化」是本店與量產茶廠的結構性差異，值得放大成賣點
3. **它完全符合決策 ① 方案 B**：沒有一個溫度或時數，卻極度具體

`optional` 態的文案 SHALL 用這段判斷依據，不得退化為「有時候會焙」。

> 商品面的連帶發現（非本 change 範圍，另行回報）：高山烏龍既然分生茶與焙茶兩種賣法，`src/data/products.ts` 目前並未呈現此區別。這可能是未被網站呈現的商品選項。

**步驟數（10–12）為什麼可接受**：使用者不是逐步讀 12 格，而是讀「4 + 2~3 + 4~5」三段，再加「炒菁擺哪裡」一句。三段結構正是讓步驟數可以誠實展開而不壓垮讀者的原因——若攤平成無分段的 12 步清單，這個設計就失敗了。

四態定義：

- **共通**（`common`）：此茶有這一步，用共通描述
- **強化／特有**（`accent`）：此茶在這一步有專屬做法，顯示專屬文案並加視覺強調
- **跳過**（`skipped`）：此茶沒有這一步，卡片**保留但降階顯示**（劃線／低透明度），且必須給出原因
- **選配**（`optional`）：此茶視批次決定做或不做，卡片正常顯示但加註條件，並說明**判斷依據**（見 1.2.2）

> `skipped` 保留卡片而非隱藏，是本設計的核心。隱藏＝使用者不知道少了什麼；保留並說明＝製造對比記憶點。
> `skipped` 出現在分歧段（炒菁、發酵）與共通後段的焙火（四季春）；`optional` 目前只出現在焙火。

### 1.4 工藝取捨（專業感的來源）

每款茶一則「為什麼要這樣做」。**全數經店主校對確認（tasks 0.10 於 2026-07-30 結案）**：

- **蜜香紅茶**：第一天當烏龍做、第二天當紅茶做，最後又回到烏龍的擠壓機與布球團揉——它是兩種工法接起來的茶。蜜香來自小綠葉蟬叮咬後茶樹的防禦反應（著蜒），所以這款茶要的是**留住小綠葉蟬**；其他病蟲害該防的還是要防
  > **更正紀錄（經店主更正，2026-07-30）**：初稿寫「**要蜜香就不能用藥**」——錯，且這是對外的農藥宣稱，風險高。店主指出仍會用藥防治小綠葉蟬以外的病蟲害，**不得寫成不用藥**。已改寫，並加測試釘住（`tea-process.test.ts`）防止復發。
- **焙火這一步在家裡做**：初製在茶廠、精製回家用箱型焙茶機慢慢調風味。這是台灣茶初製／精製分工的真實樣貌，也是「職人親手把關」這句話的具體落點——它不是形容詞，是一台機器和一個人
- **焙火是有代價的**：焙得好，茶更甜、更厚實、品質更穩定；焙過頭，花香與鮮度就沒了。承認這個代價，比「精心焙製」有說服力得多（完整文案方向見 1.2.2）
- **金萱**：只淺焙——**淺焙不會讓奶香消失**。要到**中焙**才會把奶香轉成比較奶油的味道（不是失去，是換了一種樣子）；焙到**重焙**，奶香才會被焙火味蓋過去
  > **更正紀錄（三處，均經店主更正）**：初稿寫「金萱是五款裡焙得最輕的」——錯，四季春完全不焙、高山烏龍與蜜香紅茶同為淺焙。初稿又推論「乳香是揮發性成分，焙火一重就蓋掉」——亦錯。2026-07-25 依店主說法改為「淺焙使奶香轉為奶油香」，**2026-07-30 店主再次更正：轉成奶油味的是中焙，不是淺焙**。三階段應為 淺焙＝奶香保留／中焙＝轉奶油味／重焙＝被焙火味蓋過。
- **紅烏龍**：重發酵之後**仍然炒菁**，是它與紅茶的分水嶺——把氧化按下暫停鍵，保住烏龍的甘韻。鹿野是紅烏龍的**發源地**（此點經店主確認無誤）
- **高山烏龍**：高山的環境變數多，所以烏龍**更看重製茶技術**——技術到了，品質才穩定得下來。製茶廠**不在茶園旁**，而在日照充足的區域，日光萎凋因此好做。風味則會因每年氣候稍有差異：差不多，但確實不一樣
  > **更正紀錄（經店主更正，2026-07-30）**：初稿寫「日光萎凋看天走，不是照表操課」「同一款茶，今年跟去年的做法未必一樣」——**讀起來像品質不穩**，與實情相反。店主指出：正因高山環境變數多才更靠技術，有技術才能品質穩定；且製茶廠位於日照充足處，日光萎凋反而好做。逐年差異只在風味，不在品質。
- **四季春**：價格親民有兩個結構性原因，**主要是機採**（機器採收成本遠低於手採），再加上品種早生、一年可採多次。這是成本結構的差異，不是品質妥協
  > **更正紀錄（經店主更正，2026-07-30）**：初稿只寫「品種早生、一年可採多次」——不完整，漏了**最主要的機採**因素。
  >
  > **連帶待處理**：既然四季春是機採，共通段的 `steps.pick` 文案（以手採口吻描述「一心二葉是拿捏的基準」）對這款茶並不成立。是否要為 `sijichun` 的 `pick` 加 accent 說明機採，取決於 tasks 6.6.4「共通段可否有 accent」的裁決，故暫未處理——見 tasks 0.11。

### 1.5 產地誠實標示（合作茶農）

四季春（南投名間松柏嶺）與紅烏龍（台東鹿野）為**同輩茶農以合作方式供應**，非自家製作。全站既有文案強調「自產自銷」，若製程頁以「我們的師傅這樣做」一體敘述，對這兩款不成立。

**設計立場：主動標示，並把它寫成優勢而非免責聲明。**

理由是這兩個產地並非隨意選擇，而是各自茶類的原產地——名間松柏嶺是台灣四季春主產區，鹿野是紅烏龍的發源地。因此敘事定調為**「每一款茶，都選它的原產地」**，而非「自家做不完所以外調」。

實作要求：

- 每款茶顯示**來源徽章**：`自家茶園．阿里山梅山` ／ `合作茶農．南投名間松柏嶺`
- 合作款的製程敘述改用產地口吻（「松柏嶺的做法」），與自家三款的第一人稱區隔
- 徽章為中性資訊樣式（非警示色），與其他規格標籤同級
- 此標示同時降低產地標示不實的合規風險——主動揭露即無爭議

### 2.1 分歧段的視覺處理

分歧段是本頁的重點，需與共通段明顯區隔：

- 共通前／後段：白底卡片，一般樣式
- 分歧段：**整段加底色容器**（`bg-tea-green-mist`）並加標題「這裡，五款茶分道揚鑣」
- 分歧段內的 `skipped` 卡片：劃線 + `opacity-50`，並顯示 `skipReason`
- 切換茶款時，**只有分歧段的內容變動**，共通段保持不動——強化「差別只在這裡」的認知

### 2.2 兩層 sticky 的處理

現況已有一層 sticky 步驟導覽（`ProcessContent.tsx:138`，動態同步 header 底部）。再加一層茶款選擇器會吃掉手機過多垂直空間。

**決定**：茶款選擇器與步驟導覽**合併為單一 sticky 容器**，上排茶款（5 顆）、下排工序。工序列於窄螢幕改為橫向捲動（`overflow-x-auto`），不用現行 `grid-cols-4` 兩排（工序數已增至 9–10，grid 會變三排過高）。

現有的 `stepBarRef` top 同步與 `IntersectionObserver` 捲動高亮（`ProcessContent.tsx:56-117`）整段保留，只換內容不重寫機制。

### 2.3 切換茶款時的動效

- 分歧段卡片以 `transition-all duration-300` 做狀態轉場，**不整段 unmount/remount**——要讓使用者看見「炒菁那格被劃掉」的過程，這是設計意圖所在
- 切換後捲動位置維持不變（不自動回頂），使用者可停在分歧段比較不同茶
- `prefers-reduced-motion: reduce` 時停用轉場

## 4. 資料結構

新增 `src/data/tea-process.ts`，把「哪款茶走哪條路徑」從 JSX 抽離為資料，避免 5×10 的條件判斷散在元件裡：

```ts
export type StepState = "common" | "accent" | "skipped" | "optional";
export type TeaKey    = "oolong" | "jinxuan" | "sijichun" | "black" | "redOolong";
export type FamilyKey = "partialBall" | "fullBall" | "heavyBall";
export type Sourcing  = "own" | "partner";

export interface TeaProcess {
  key: TeaKey;
  family: FamilyKey;
  productId: number;              // 對應 src/data/products.ts，供 CTA 導流
  sourcing: Sourcing;             // 自家茶園 / 合作茶農
  divergence: StepKey[];          // 分歧段的實際順序（因茶而異）
  skipped: StepKey[];             // 跳過的工序（分歧段的炒菁/發酵、四季春的焙火）
  optional: StepKey[];            // 視批次決定的工序（目前僅 roast）
  accents: StepKey[];             // 有專屬做法的工序
}
```

共通前後段的順序寫成模組常數（所有茶共用），**只有分歧段是 per-tea 資料**——資料結構直接反映第 0 節的洞察。焙火雖位於共通後段，但其狀態為 per-tea（見 1.2.2），故以 `skipped`／`optional` 兩份清單覆寫共通段的預設值。

文案一律走 i18n，此檔只存結構與關聯。i18n key 命名：

- 共通工序文案：沿用現有 `process.steps.<stepKey>.{name,desc,detail}`
- 茶款專屬文案：`process.teaSteps.<teaKey>.<stepKey>.{desc,detail}`（僅 `accent` 需要）
- 跳過原因：`process.teaSteps.<teaKey>.<stepKey>.skipReason`
- 家族：`process.families.<familyKey>.{name,desc}`
- 分歧段標題與說明：`process.divergence.*`
- 來源徽章：`process.sourcing.{own,partner}`
- 對照表：`process.matrix.*`

`zh.json` 與 `en.json` 必須完全對稱（現況已對稱，47 個葉節點，不可退化）。

## 5. 結構化資料

每款茶輸出一份 `HowTo`（`schema.org/HowTo`），`step` **依該茶的實際順序**排列，`skipped` 工序不進 JSON-LD——結構化資料描述的是真實作法，不是教學對比。

- 序列化一律經 `src/lib/seo.ts` 的 `jsonLdString()`（既有慣例，防 `</script>` 突破）
- metadata 沿用 `langAlternates("/process")`
- `HowTo.name` 依 locale 對應中英，與 `products.ts` 的 `name`／`nameEn` 一致
- 每款茶區段加 `id` anchor（如 `/process#black`），讓 AI 可引用到段落層級
