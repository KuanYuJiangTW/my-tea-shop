## Context

`getExperienceTypes()` 與 `getProducts()` 都是 `.order("id")`，順序等於建立順序。萬鷺朝鳳・茶山導覽是 id 6（線上實際資料：450 元／1.5 小時，20 筆場次落在 2026-08-18 至 2026-10-11），因此在它唯一有場次的 51 天裡排在最後一張。

今年是這款體驗第一次放上自有網站，業主明確表示每年現場人都很多——也就是**需求是真的，缺的是把它導到線上的路徑**。季節內的曝光位置在這種情況下直接等於營收。

限制：本專案無 CLI migration 流程，SQL 由業主在 Supabase SQL Editor 執行；`experience_types.id` 被 `experience_sessions`、`experience_bookings`、`experience_reviews` 三張表以外鍵引用。

## Goals / Non-Goals

**Goals:**

- 季節內的體驗自動排到最前面，季節結束自動退回，**不依賴任何人記得去調**。
- 業主能在後台調整平時順序，並做有到期日的臨時釘選。
- 季節資料只有一份，與 `experience-open-class-request` 的「可申請期間」是同一張表。
- 季節狀態在前台看得見（徽章、倒數、季節外的「明年見」與通知我）。

**Non-Goals:**

- 不改任何主鍵 id。
- 不做自動開場次、不做依熱度／評價的排序引擎。
- 不改動既有的場次、預約、評價行為。

## Decisions

### D1：排序鍵的順序是「釘選 → 季節 → 手動 → id」

```sql
ORDER BY
  CASE WHEN pinned_until >= CURRENT_DATE THEN 0 ELSE 1 END,
  CASE WHEN <今天落在該款任一季節區間> THEN 0 ELSE 1 END,
  sort_order,
  id
```

**為什麼釘選在季節之前**：釘選是業主針對當下狀況（媒體報導、鳥況特別好、連假）的明確意圖，應該壓過通則。**為什麼 id 墊底**：任何兩款的其他鍵都相同時要有穩定的最終順序，否則列表順序會在不同查詢間跳動。

### D2：釘選一定要有到期日，不提供「永久置頂」

`pinned_until` 是 `DATE` 而非 `BOOLEAN`。後台的釘選 UI 必須選一個日期才能送出。

**理由**：布林值的置頂在人的記憶裡沒有到期日。這個功能一年只會用到兩三次，用到的當下都是忙的時候（季節剛開始、報導剛出來），撤下的時機則沒有任何事件提醒。**把到期日變成必填，是用資料結構取代記憶。**

### D3：排序集中在單一純函式，不建資料庫 view

**選擇**：`getExperienceTypes()` 一次查詢帶出體驗與其季節區間（PostgREST embedded resource），排序交給 `src/lib/experience-ordering.ts` 的 `sortExperiences()`。**所有讀取路徑都經過 `getExperienceTypes()`，所以排序只有一份。**

**原本的規劃是建 `experience_types_ordered` view，實作時改掉，理由有三**：

1. **本專案沒有 migration 流程，SQL 由業主手動貼上執行。** 少一個資料庫物件就少一件會出錯、會漏掉、日後沒人記得它存在的東西。增欄與建表已經是必要的，view 不是。
2. **部署順序耦合**：程式若查一個還不存在的 view，`getExperienceTypes()` 會回空陣列，體驗列表整頁空白。純函式版本在欄位還沒建好時，只是拿不到 `sort_order`（`undefined` 排序穩定退回 id 順序），**壞的方向是安全的**。
3. **時區邏輯測得到**。季節判定要用台灣時間（見 Risks），寫在 SQL 裡只能靠實際連線驗證；寫在 TS 裡可以用 vitest 固定「台灣時間季節首日 07:00、UTC 仍是前一日」這種邊界。

**原本選 view 的理由（多個呼叫點各排各的）仍然成立，但真正的解法是「只有一個呼叫點」，不是「把邏輯推到資料庫」。** 首頁、列表頁、後台一律呼叫 `getExperienceTypes()`，不得自己查 `experience_types` 再排。

### D4：季節結束後卡片不下架，改為「明年見 ＋ 留 Email 通知」

**替代方案**：季節外把該款 `is_active` 設 false 隱藏。**不採用**——那會讓一年中十個月完全看不到這個商品，也失去累積名單的機會。今年第一次上線，**季節外的流量拿來累積明年的名單，價值高於把版面讓給其他五款**。

「留 Email 通知我」的收件名單與 `experience-open-class-request` 的需求蒐集是同一件事，兩者實作時共用同一張表（該 change 的 `experience_requests`，或其 Phase 0 的輕量版）。**先實作的一方建表，後者沿用。**

### D5：商品沿用同一套 `sort_order`，但不做季節

`products` 只加 `sort_order`，不加季節區間。

**理由**：茶葉的季節性是「上市」而非「限時開放」——冬茶上市後不會下架。上市推廣用 `sort_order` 手動調就夠，硬套季節區間會逼業主為每款茶維護一組沒有實際結束日的日期。**同一個機制不見得該套用到每個地方。**

## Risks / Trade-offs

- **季節區間忘記續填** → 該款回到原位，等同現狀，不會出錯。後台在最後一段季節結束日距今不到 30 天時顯示提醒（與 `experience-open-class-request` 共用同一個提醒）。
- **季節區間跨年（例如 12/20–1/10）** → 以「多段區間」表達，不做跨年單段；判定一律是 `CURRENT_DATE BETWEEN start_date AND end_date`，避免跨年邏輯的邊界錯誤。
- **時區** → 季節判定用資料庫的 `CURRENT_DATE`。Supabase 預設 UTC，而台灣是 UTC+8，**季節首日與末日會有 8 小時的落差**。判定一律用台灣時間的當日日期（`(now() AT TIME ZONE 'Asia/Taipei')::date`），並在測試中固定首日與末日兩個邊界。
- **排序邏輯散到多個呼叫點** → 唯一的防線是「只有 `getExperienceTypes()` 會排序」。任何直接查 `experience_types` 再自己排的地方都是缺陷，測試要涵蓋排序結果（給定三款體驗與各自狀態，斷言順序）。
- **釘選與季節同時存在造成困惑** → 後台在釘選其他款時，若當下有季節中的體驗被壓下去，顯示提示告知目前排序結果。

## Migration Plan

1. 業主執行 `supabase/add_experience_ordering.sql`：兩張表增欄（`ADD COLUMN IF NOT EXISTS`）、建季節表（若 `experience-open-class-request` 已建則跳過）、建 view。
2. 增欄後 `sort_order` 全為預設 100、`pinned_until` 全為 NULL、季節表為空——**排序結果與現在完全相同**（退回 id 順序）。
3. 部署程式碼，前台行為不變。
4. 業主填入萬鷺朝鳳的季節區間（8/18–10/11），該款即自動置頂並顯示倒數。
5. 回滾：清空季節表並將 `sort_order` 全設回 100，即回到 id 順序。

## Open Questions

三題原本的疑問已由業主於 2026-08-21 回答，記錄如下：

1. **萬鷺朝鳳的季節區間為 8/18 – 10/11**，業主確認這是完整鳥況期（不是只排到這裡）。注意首日 8/18 已經過去，**本季只剩到 10/11**——這決定了本 change 的時效價值。
2. **季節外的「開放時通知我」與 `experience-open-class-request` 的需求蒐集合併為同一個入口**，不做兩個長得一樣的表單。
3. **平時順序維持現行 id 順序**，等有實績再依熱門度調整。

仍未定：

- 採茶與紅茶製作的區間起訖日需要業主指定確切日期（業主給的是「3 月底–7 月底、9 月中–11 月底」且註明「沒有很固定」）。**這不阻擋實作**——後台可隨時調整，先填近似值即可。
- 萬鷺朝鳳的 10:00 場次是否保留（鳥況為 15:00–18:00，早上場看不到鳥）。與排序無關，但同屬該款的呈現問題，見 `experience-open-class-request` 提案的「賞鳥的 3 小時」一節。
