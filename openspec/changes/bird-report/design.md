## Context

賞鳥客人最大的顧慮是白跑一趟——梅山交流道開上來要 44 分鐘，嘉義市區要一小時。一則第一手的「昨天下午鳥況如何」能直接消掉那個顧慮，而且只有住在賞鳥起點的人給得出來。

現況與限制：

- 本 repo **沒有 migration 工具**，`supabase/*.sql` 由業主自行在 SQL Editor 貼上執行。程式碼與 schema 必然有一段不同步的時間（見 `lessons.md` 2026-08-23：兩支 SQL 有順序相依時用 `information_schema` 解，不要寫在註解裡）
- 後台已有一套權限（`withAdminAuth`）與版面（`src/app/admin/(protected)/`），沿用即可
- 季節判斷已有一套（`experience-seasonal-ordering` 的 `experience_availability_windows` ＋ `src/lib/experience-ordering`），不應另立
- 業主每天要用，而且是在**手機上**用。更新成本超過十秒就不會有人做，功能等於不存在

## Goals / Non-Goals

**Goals:**
- 業主在手機上十秒內送出一則鳥況
- 過期與季節閘門**全自動**，業主不需要記得撤下任何東西
- 資料表還沒建立時全站照常運作
- 對外顯示一律附回報時間

**Non-Goals:**
- 不做鳥況等級／顏色標籤。第一版只有自由文字——業主的口吻本身就是這個品牌最強的東西，下拉選單會把它磨掉。等真的嫌打字麻煩再說
- 不做定時提醒業主更新。48 小時自動消失已經處理了「忘記」，再加推播是把成本轉嫁給業主
- 不做歷史鳥況的對外呈現（例如「本季鳥況月曆」）。資料留著，但這一版不顯示
- 不做多語輸入。業主用中文寫，英文頁原樣顯示

## Decisions

### 1. 資料表用 append-only，不用單列覆寫

**選擇**：`bird_reports` 資料表，每次送出 `INSERT` 一列；對外取 `ORDER BY reported_at DESC LIMIT 1`。

**替代方案**：單一列（`id = 1`）反覆 `UPDATE`。

**理由**：append-only 保留歷史，之後要做「本季鳥況回顧」不必再改 schema；而且誤送一則錯的鳥況時，補送一則正確的就蓋過去了，不需要做編輯功能。單列覆寫看似簡單，但把「更正」變成必須實作的功能。

### 2. 過期用讀取時判斷，不用排程

**選擇**：查詢時比對 `reported_at >= now() - 48 hours`，超過就當作沒有。

**替代方案**：cron 每小時把過期的標記為 inactive。

**理由**：排程是可以壞掉的東西，而它壞掉的方式正好是最糟的——過期的「鳥況良好」繼續掛在線上。讀取時判斷沒有這個失效模式。`vercel.json` 已經有數個 cron，不需要為此再加一個。

### 3. 48 小時這個數字

賞鳥發生在下午 2–6 點。業主傍晚六點回報，隔天要出發的人上午看到它，此時距今約 15 小時，仍然有用。到第三天上午就是 36 小時以上、資訊已經隔了一整個賞鳥日，該消失。48 小時涵蓋「昨天傍晚回報、今天全天可看」，並在隔一天的傍晚前後自然消失。

時間一律顯示，讓讀者自己判斷還準不準——這也是 48 小時可以放寬到這個長度的前提。

### 4. 季節判斷沿用 `experience_availability_windows`

**選擇**：以 `cattle-egret-tour` 這款體驗的可用區間為準，用既有的 `currentWindow()`／`isInSeason()`。

**替代方案**：在鳥況資料表加 `season_start` / `season_end` 欄位。

**理由**：日期只能有一個真相來源。體驗頁的季節徽章、排序、Event 結構化資料都已經吃那份區間，鳥況再存一份就是兩份會不同步的日期——而且不同步的那天正好是季節交界，也就是最多人在看的時候。

### 5. 後台頁面：單欄位 + 送出

一個 `textarea` 加一顆按鈕，外加「目前對外顯示的是什麼」的即時預覽（含「正在顯示／已過期／季節外」的狀態）。

那個狀態顯示是刻意的：業主打開頁面時第一個問題永遠是「現在網站上寫的是什麼」。沒有它，業主會因為不確定而重複送出。

### 6. 資料表不存在時：對外靜默、後台明說

對外頁面吞掉 `42P01`／`42703` 當作沒有回報——訪客不需要知道站方的 SQL 還沒跑。後台則回 503 並指名 `supabase/add_bird_report.sql`，因為那正是能解決問題的人在看。

這與 `src/app/api/admin/experience-ordering/route.ts` 既有的處理一致。

## Risks / Trade-offs

**[業主寫了會被誤解的內容]** → 這是自由文字的代價。用後台頁面上的一行提示降低：「寫事實不要寫評價——『下午下雨，四點後零星幾隻』比『鳥況很差』有用」。不做內容審核，那會讓十秒鐘變成三十秒。

**[伺服器時區與台北時區不一致，導致過期或季節判斷差一天]** → 全部用 `reported_at` 的絕對時間戳做 48 小時比較（不涉及日曆日），季節則沿用既有的 `taipeiToday()`。這兩者本來就已經處理過時區。

**[業主整季只寫一次就放棄]** → 這是最可能的失敗模式，而它不是技術問題。降低的方式只有把更新成本壓到十秒。上線後若一週內沒有第二則，應該視為設計失敗並重新檢討，而不是催促業主。

**[append-only 資料無限成長]** → 一季最多幾十列，十年也是幾百列。不處理。

**[誤送一則錯的鳥況]** → 補送一則正確的即可蓋過。不做刪除功能——刪除在對外事實上是更危險的操作，而補送已經足夠。

## Migration Plan

1. 合併程式碼。此時資料表還不存在，對外頁面完全不顯示鳥況，後台頁面顯示 503 提示——**站上沒有任何行為改變**
2. 業主在 Supabase SQL Editor 執行 `supabase/add_bird_report.sql`（可重複執行）
3. 業主在後台送出第一則，確認對外頁面出現
4. 回滾：不需要回滾程式碼。停用只要不再更新，48 小時後自動消失
