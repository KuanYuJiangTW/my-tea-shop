## Context

霧抉茶是 Next.js App Router + Supabase 的茶葉電商，前台支援中英文（next-intl），有商品購買、茶山體驗預約等功能。目前沒有任何即時問答機制。商品數量不多（約 10-20 款茶），體驗活動 5 種，知識範圍有限且可控，適合直接塞進 system prompt 而非建置向量資料庫。

## Goals / Non-Goals

**Goals:**
- 提供 24 小時即時 AI 問答，回答茶葉知識、商品推薦、體驗活動細節
- 使用 Gemini API 免費方案，零額外成本
- 串流回應，使用者體驗流暢
- 支援中英文雙語
- AI 回答限定在茶葉相關範圍，無法回答時引導聯繫真人
- 對話以 sessionStorage 暫存，關閉瀏覽器分頁才清除（切頁或關閉再開視窗都保留）

**Non-Goals:**
- 不做客服系統（退換貨、訂單查詢、物流追蹤）
- 不做代客下單或修改訂單
- 不建置向量資料庫或 RAG pipeline
- 不儲存對話記錄到資料庫
- 不做使用者身份識別（匿名即可使用）
- 不做 Admin 後台的知識庫管理介面（初期硬編碼）

## Decisions

### 1. AI 模型：Gemini 2.0 Flash

**選擇**：`gemini-2.0-flash`（Google Gemini API 免費方案）

**替代方案**：
| 方案 | 優點 | 缺點 |
|---|---|---|
| Claude Haiku | 回答品質好 | 需付費（~$3-5/月） |
| Groq (Llama) | 免費、極快 | 中文品質較差 |
| Gemini Flash | 免費額度大、中文品質好 | Google 生態綁定 |

**理由**：免費額度最大（15 RPM、100 萬 tokens/分鐘），中文回答品質夠好，對小型電商綽綽有餘。未來流量增大可無痛切換到付費方案或 Claude。

### 2. 知識庫策略：System Prompt 硬編碼

**選擇**：將商品資料、體驗活動、常見問答直接寫成結構化文字，塞進 system prompt。

**替代方案**：向量資料庫 + RAG（Pinecone / Supabase pgvector）

**理由**：商品數量少（< 20），體驗活動固定（5 種），全部資訊加起來約 2000-3000 tokens，遠低於 Gemini 的 context window。RAG 增加複雜度但無實質收益。當商品超過 50 款或需要動態更新時再考慮 RAG。

### 3. 知識庫內容來源：API 動態讀取

**選擇**：`/api/chat` 每次請求時從 Supabase 讀取最新商品與體驗資料，組合成 system prompt。

**替代方案**：硬編碼靜態文字

**理由**：商品價格、庫存、體驗場次會變動，靜態文字容易過期導致 AI 給出錯誤資訊。從資料庫即時讀取確保資訊正確。加上快取（60 秒 revalidate）避免頻繁查詢。

### 4. UI 模式：浮動按鈕 + 半屏對話視窗

**選擇**：右下角浮動圓形按鈕，點擊後展開固定尺寸對話視窗（桌面 380×520px，手機底部半屏）。

**理由**：
- 不自動彈出，避免干擾瀏覽體驗
- 半屏設計讓用戶可同時看到網頁內容
- 開啟時顯示 AI 歡迎訊息 + 依當前頁面動態切換的快捷問題，降低使用門檻
- 手機版按鈕位置需避開底部固定 CTA 按鈕（加入購物車、立即預約等），適當上移

### 5. 串流回應：Server-Sent Events

**選擇**：API Route 使用 `ReadableStream` 回傳串流，前端用 `fetch` + `ReadableStream` 逐步讀取。

**替代方案**：WebSocket、完整回應後一次顯示

**理由**：SSE 實作最簡單，Next.js API Route 原生支援，不需額外設定 WebSocket 伺服器。串流回應讓用戶感受更快的回覆速度。

### 6. 對話上下文：sessionStorage 暫存

**選擇**：對話紀錄存入 `sessionStorage`，每次請求帶最近 10 則訊息作為 context。關閉瀏覽器分頁才清除。

**替代方案**：React state 暫存（關閉視窗即清除）

**理由**：用戶常不小心關掉對話視窗或切換頁面，state 暫存會讓對話全部消失，體驗很差。sessionStorage 在同一分頁內持久保留，關閉分頁才清除，兼顧便利性與隱私。不儲存到資料庫，零額外成本。

### 8. 快捷問題：依頁面動態切換

**選擇**：根據用戶當前所在頁面，顯示不同的快捷問題。

**替代方案**：全站固定 3 個快捷問題

**理由**：用戶在商品頁時想問的是「這款茶的特色」，在體驗頁時想問的是「適合幾歲參加」。固定問題無法對應情境，動態切換讓快捷問題更有用。

頁面對應：
- 首頁 / 其他頁面：推薦送禮茶葉 / 體驗活動有哪些 / 如何泡出好茶
- 商品列表 / 商品頁：這款茶的風味特色 / 適合搭配什麼食物 / 送禮包裝有嗎
- 體驗列表 / 體驗頁：適合幾歲參加 / 需要自備什麼 / 下雨天照常嗎

### 9. 轉真人：LINE 連結按鈕

**選擇**：AI 無法回答時，在對話中直接渲染可點擊的 LINE 官方帳號連結按鈕。

**替代方案**：純文字提示「請加 LINE」

**理由**：純文字提示需要用戶自己去找 LINE 帳號，多一步就少一個客人。嵌入可點擊按鈕，一鍵跳轉 LINE，轉換率更高。

### 10. 用量監控：簡易計數 log

**選擇**：在 API Route 中記錄每次對話請求到 console.log，格式包含時間戳和 locale。

**替代方案**：寫入 Supabase / 外部監控服務

**理由**：初期只需知道大致用量，Vercel 的 Function Logs 可直接查看。等需求增長再考慮結構化監控。

### 7. 速率限制：前端節流 + 後端檢查

**選擇**：前端限制每 2 秒最多送出 1 則訊息，後端以 IP 為單位限制每分鐘 10 則。

**理由**：防止濫用，保護 Gemini API 免費額度。前端節流提升體驗（避免重複送出），後端檢查防止繞過前端限制。

## Risks / Trade-offs

| 風險 | 緩解方式 |
|------|----------|
| Gemini 免費額度用完（15 RPM） | 前後端速率限制 + 監控用量，超限時顯示「目前較忙，請稍後再試」 |
| AI 瞎編商品資訊（幻覺） | System prompt 嚴格限定：「只根據提供的商品資料回答，不確定就說不知道」 |
| AI 回答非茶葉相關問題 | System prompt 限定角色：「你是霧抉茶的茶葉顧問，只回答茶葉相關問題」 |
| 商品資料更新後 AI 未同步 | 從資料庫即時讀取 + 60 秒快取，確保資料新鮮度 |
| Gemini API 服務中斷 | 前端顯示友善錯誤訊息，引導聯繫 LINE 官方帳號 |
| 手機鍵盤彈出遮擋對話視窗 | 手機版對話視窗使用 `dvh` 單位，鍵盤彈出時自動調整高度 |
| 手機聊天按鈕遮擋 CTA 按鈕 | 偵測頁面底部固定元素，按鈕適當上移避開 |
