# 技術設計：客製開課請求

## Context

現況：`experience_sessions` 由後台手動建立，前台月曆（`ExperienceCalendar.tsx`）只呈現既有場次，沒有場次的日期是純空白。既有機制中有三件事可以直接複用，設計應該圍繞它們展開，而不是另起爐灶：

1. **`expire-pending-bookings` cron**（每日 03:30 UTC）已經在收「建立超過 24 小時仍未付款」的預約——這正是防跳票需要的機制，不必為開課請求另做訂金流程。
2. **`web_inquiries` 的匿名表單模式**（service_role 寫入、RLS deny-by-default、rate limit、honeypot、白名單驗證、admin 通知信 best-effort）已經跑在線上，開課請求的表單可以整套沿用。
3. **`sendAdminPendingRefundDigest`** 的每日彙整信模式，正好是「待審請求積壓提醒」要的東西。

兩件從線上資料查到、會影響設計的事實：(a) `experience_types` 實際有 **6 款**——`cattle-egret-tour`「萬鷺朝鳳・茶山導覽」早就上線並排了 20 場（8/22–10/11），`supabase/booking_schema.sql` 只是初始 seed，**不反映線上現況**；(b) 體驗預約至今 29 筆全部來自業主自己的信箱，**真實客人成交 0 筆**。(b) 決定了這個功能該做多大——見 proposal 的「現況數據」與 Phase 0 建議。

限制：正式營運中，改動會影響真實訂單與金流；本專案沒有 CLI migration 流程，SQL 由業主在 Supabase SQL Editor 執行；沒有任何「站台設定」資料表，可調參數只能放在既有資料表的欄位上。

## Goals / Non-Goals

**Goals:**

- 把「月曆上找不到日期」從死路變成一條有紀錄、可追蹤、可統計的成交路徑。
- 業主的每一筆審核都能在**一個畫面內**完成決策（含同日期需求聚合、與既有場次的衝突提示、一鍵聯絡）。
- 核准後**不需要人工再建場次**：系統建場次、發連結、催付款、逾期回收，全自動。
- 未成交的請求也要留下價值：哪些日期、哪些體驗最多人問，以及可主動回頭通知的名單。
- 全流程雙語（zh-TW／EN），不得寫死中文字串。

**Non-Goals:**

- 不做訂金金流、不做企業包場專屬表單、不做發起人招生獎勵、不做免審核的全自動排程（理由見 proposal 的「刻意不做」）。
- 不改動既有場次、預約、候補、點數、退款的任何行為。

## Decisions

### D1：不收訂金，用「核准 → 專屬連結 48 小時 → 既有 24 小時付款 cron」防跳票

**選擇**：請求階段完全免費；核准後寄出帶 token 的專屬預約連結（48 小時有效），客人點進去走既有預約流程建立 `pending_payment` 預約，之後由既有 `expire-pending-bookings` 接手。

**為什麼不收訂金**：訂金要串金流、要對帳、要退款規則、要處理「訂金能不能抵扣」——複雜度高一個量級，而它換到的東西（客人的承諾）用「不付款就沒有這一天」同樣拿得到。**兩層期限**（連結 48 小時、預約 24 小時）在客人端讀起來只有一句話：「兩天內完成付款，這天才算保留給你」。

**代價**：業主核准後、客人付款前，那個日期時段被 `UNIQUE (experience_type_id, session_date, start_time)` 佔住。可接受——逾期會自動回收，而且期間場次是 private，不會誤導其他客人。

### D2：申請不要求登入，用 token 做自助查詢與撤回

**選擇**：`POST /api/experience-requests` 接受匿名提交（`user_id` 可為 null）；回傳一組不可猜的 token，客人憑 `/experiences/request/[token]` 查詢狀態、撤回、選替代方案。**付款階段才需要登入**，沿用既有預約流程（`POST /api/bookings` 本來就擋未登入）。

**替代方案**：要求登入才能送出。品質高、可直接綁 `user_id`，但會砍掉可觀的送出量——而這個功能的價值正是**捕捉那些原本會直接關掉分頁的人**，在入口設帳號牆等於自廢武功。

**token 規格**：32 bytes crypto random → base64url，DB unique 欄位，帶到期時間。承載查詢、撤回、選替代方案、預約四種用途，權限一律以 token 對應的那一筆請求為界。頁面 `noindex`、不進 sitemap。

### D3：門檻是「開團最低名額數」，並採買斷名額制

**選擇**：`experience_types.request_min_slots` 定義該體驗客製開課的最低名額數（整數）。客人付 `request_min_slots × price`，換到的是**該時段的這些名額，愛帶幾個人來由他決定**（上限 `max_participants`）。

**為什麼是名額數而不是金額**：金額門檻要換算成人數才看得懂（「3,150 元？那是幾個人？」），而且遇到平日折扣就會出現 2.4 人這種說不出口的數字。名額數對客人是一句話：「這款開一場最少 2 個名額，你可以自己帶滿。」對後端也少一層換算。

**為什麼是買斷而不是補差額**：若讓 1 個人付「1 人份＋開團費」，同一場後來加入的人單價較低，會產生「我付比較貴」的客訴，而且退不退開團費又是一套規則。買斷名額制把它變成一句不需要解釋的話——**他買的是位子，不是比較貴的票**。它也剛好回答了「採茶 1 個人也能帶」：能帶，但付的是 2 個名額。

**刻意不做平日折扣**：這種金額的體驗，折 90 元不會改變任何人的決策，卻會讓「最低名額數」這個乾淨的規則長出一堆例外。要提客單價該用「同日加購第二個體驗 9 折」，那才對得上真正的成本結構（客人已經上山了）。

### D4：核准即建立場次，用 `visibility` 控制曝光，不做名額保留（seat hold）

**選擇**：核准時直接 `INSERT experience_sessions`，帶 `visibility = 'private'`、`created_from_request_id`。發起人完成付款後，若請求非包場，場次轉為 `visibility = 'public'` 進入公開月曆，其他客人可加入併團；逾期未付款則場次刪除或標記 `cancelled`。

**替代方案**：先在場次上「保留 N 個名額」給發起人。需要新的名額保留邏輯，還要跟既有的 `current_participants` trigger（只計 `confirmed`）打架。**private → public 的可見性切換達到同樣效果，且完全不動既有的名額計算**。

**衝突檢查**：核准前查該 `(experience_type_id, session_date, start_time)` 是否已有場次。已有則不建新場次，改為提示業主「這天這個時段已經有場次了」並提供「請客人加入既有場次」的一鍵回覆（帶該場次連結）——這比讓 UNIQUE 約束丟錯誤好得多，而且那本來就是更好的結果。

### D5：狀態機

```
pending ──approve──────────► approved ──客人付款──► converted
   │                            │
   │                            └──48h 未使用連結──► expired
   ├──offer-alternative──► alternative_offered ──客人選了──► approved
   │                            └──7 天未回應──► expired
   ├──decline───────────► declined
   └──客人撤回──────────► withdrawn
```

`converted` 是終局：請求已變成一筆真實預約（`session_id` 與 `booking_id` 都填上）。統計漏斗（送出 → 核准 → 成交）直接查這張表就有。

### D6：可調參數放既有資料表欄位，不新增 settings 表

`experience_types` 增三欄：`accepts_requests`（開關，**預設 false**）、`request_min_revenue`、`request_lead_days`。公休日另立 `experience_blackout_dates`。

**理由**：專案沒有既有的設定儲存機制，為三個參數蓋一張 key-value settings 表會引入一個沒人維護的新概念；掛在 `experience_types` 上還有一個好處——**每款體驗可以獨立開關**，於是能先只開茶藝體驗試跑（見 Migration Plan）。

### D7：不沿用 `waitlist_entries`

候補綁的是**已存在的場次**（`session_id` NOT NULL），開課請求的前提正好是「沒有場次」。硬塞會讓 `session_id` 變成可空欄位、讓候補的通知與確認邏輯要處處分辨兩種語意。**兩者互補而非重疊**：候補是「這場我想擠進去」，請求是「請為我開一場」。分開兩張表，各自乾淨。

### D8：需求標記只回聚合數字，且滿 2 人才顯示

`GET /api/experience-requests/demand?slug=&year=&month=` 只回 `{ date, startTime, headcount, requestCount }`，**不回姓名、電話、Email，也不回是誰**。

**滿 2 人才顯示**：只有 1 個人想開課時，標記傳達的訊息是「只有你想」——那是負面社會證明，會降低而不是提高附議意願。門檻設 2 讓標記出現時永遠是正向訊號。

### D9：資料表 RLS 一律 deny-by-default

三張新表比照 `web_inquiries`：`ENABLE ROW LEVEL SECURITY` 且**不建立任何 anon／authenticated policy**，讀寫全部經 API route 的 service_role client。客人的自助查詢頁走 API + token，不讓瀏覽器直連。

### D10：i18n 從第一行就雙語

新增 `experienceRequest` 命名空間，zh／en 同時建立。**不得出現寫死中文的 UI 文案、`alt`、`aria-label`**——`.claude/playbooks/lessons.md` 與最近兩次 SEO／a11y 修正都是在補這個債，這次不要再欠。信件樣板依 `experience_requests.locale` 決定語言（`web_inquiries` 已有相同欄位可參照）。

### D11：季節限制用「可申請期間」，不用黑名單反過來填

**選擇**：新表 `experience_availability_windows(experience_type_id, start_date, end_date, note)`，一款體驗可有多段。**這張表與 `experience-seasonal-ordering`（季節內自動把該款排到第一張）共用**——同一份季節設定同時決定「能不能申請」與「排在哪」，業主只維護一處。誰先實作誰建表。**有設定 window 的體驗＝白名單制**（只有落在任一段內的日期可申請）；**沒設定 window 的體驗＝不限期間**，仍受黑名單與前置天數約束。

**為什麼不用黑名單表達**：採茶一年只有幾段可採期、黃頭鷺只有賞鳥季——用黑名單要填掉全年三百多天，而且每年都要重填。白名單只要填那幾段，而且過期了很明顯（沒有涵蓋未來日期＝該款自動關閉申請），**遺漏會讓功能安全地關掉，而不是安全地開著**。

**UI 上不能只是「不能選」**：日期不可選時要說明原因並指向最近的可申請期間（「這段期間茶園沒有新芽可採，最近的可採期是 4/15–5/10」）。客人知道什麼時候該回來，比單純被擋住有價值得多。

### D12：時段白名單是每款體驗自己的，不是全站常數

**選擇**：`experience_types.request_start_times`（`TEXT[]`，預設 `{'10:00','14:00'}`）。驗證時取該體驗的設定，而非全站常數。

**理由**：黃頭鷺導覽若走黃昏歸巢，時段跟其他五款完全不同；把 `10:00／14:00` 寫成全站常數，等於在資料層擋死一款商品。**這個欄位的成本是一欄，寫死的成本是之後要改動每一條驗證路徑。**

## Risks / Trade-offs

- **業主審核負擔壓垮功能** → 三道防線：(a) 前置天數／黑名單／時段白名單讓表單先擋掉不可能成交的申請；(b) 同日期聚合視圖讓多筆請求一次核准；(c) 每日 digest 讓待審不會被遺忘。若量仍過大，`accepts_requests` 可逐款關閉。
- **假單與灌爆** → rate limit（每 IP 每日上限）＋ honeypot ＋ 白名單驗證，比照 `web-inquiry`。**刻意不加 email 驗證信這一關**：多一步會流失真客人，而假單的成本只是業主多看一眼；若實際被灌爆再加。
- **核准後客人不付款，日期被卡住** → 48 小時 token 到期即回收場次；業主也能在後台手動撤銷核准。
- **「我付的錢比較多」的客訴** → 買斷名額制（D3）＋ 表單送出前就明示最低消費與名額數，成交條件在付錢之前講完。
- **private 場次外洩** → token 不可猜、頁面 noindex、`GET /api/experience-sessions` 明確過濾 `visibility = 'private'`（要有測試守住，這是最容易在後續重構中被改回去的一行）。
- **天候（黃頭鷺看不到、採茶遇雨）** → 建議條款為「遇雨可免費改期一次，不退費」，改期走既有的後台代為取消＋重新預約，或由業主手動調整場次日期；不新增自動改期機制。
- **可申請期間過期沒人續填** → 該款體驗自動變成無可申請日期（安全關閉），後台在期間剩不到 30 天時於請求管理頁顯示提醒。
- **時區** → `session_date`（date）與 `start_time`（time）沿用既有無時區設計，一律以台灣時間解讀；前置天數計算以台灣時間的當日 00:00 為基準，避免跨日誤差。
- **黑名單日期與既有場次矛盾**（業主把已有場次的日子設為公休）→ 黑名單只擋新請求，不影響既有場次；後台設定時提示該日已有場次。

## Migration Plan

1. 業主在 Supabase SQL Editor 執行 `supabase/add_experience_requests.sql`（三張新表＋兩張表的增欄，全部 `IF NOT EXISTS`）。增欄後既有場次的 `visibility` 預設 `'public'`，行為不變。
2. 部署程式碼。此時 `accepts_requests` 全為 `false`，前台入口不顯示，**等同未上線**。
3. **只開茶藝體驗一款**（`accepts_requests = true`），觀察兩週：申請量、核准率、成交率、業主每筆審核花的時間。
4. 依實測調整最低消費與前置天數，再逐款開啟。
5. 回滾：把 `accepts_requests` 全設回 `false`，前台入口即消失，已核准的請求不受影響（場次與預約已是既有機制的一部分）。**不需要回滾程式碼**。

## Open Questions

1. 六款體驗的實際變動成本與準備收拾時數——proposal 的淨貢獻表目前用估算值，拿到實數要全部重算。
2. 黃頭鷺導覽的定價、時長、時段（清晨覓食／黃昏歸巢／隨茶園農作）與賞鳥季月份。
3. 採茶每年的可採期區間。
4. 急件 +20% 的數字要不要調整（平日折扣已決定不做，見 D3）。
3. 「+1 附議」是否要限制同一 Email 對同一日期只能附議一次（傾向要，防刷高人數）。
4. 婉拒信要不要順便把人加進「該體驗開新場次時通知我」的名單——這是把失敗的請求變成資產，但需要一張訂閱表與退訂機制，可能該獨立成另一個 change。
