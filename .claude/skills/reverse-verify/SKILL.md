# 反向驗證：證明你的測試抓得到那個 bug

## 為什麼需要這件事

寫完修正、加了測試、測試全綠——這只證明**修正之後**行為正確，
**不證明測試在沒有修正時會失敗**。兩者的差距是真實事故的來源。

本專案 2026-07-28～29 的實例：

| 修正 | 有做反向驗證？ | 結果 |
|---|---|---|
| 2FA `verify()` 取 `.valid` | ✅ | 退回後錯誤驗證碼回 **200 並發 session**——測試有效 |
| admin route 授權掃描 | ✅ | 退回後指出 `orders/route.ts` GET 未保護 |
| cvs-callback XSS | ✅ | 退回後 5 條測試紅 |
| TOTP 時間容差 | ✅ | 退回後前後時窗的碼被拒 |
| **sanity-webhook 時間戳** | ❌ **漏做** | 10 條測試全過，**但單位是錯的，bug 上了 production** |

最後一列是這個 skill 存在的理由：測試用了跟程式碼**同一個錯誤假設**（把毫秒當秒），
所以自我一致地全過。只有退回修正才會暴露這種盲區——但那次連退回都沒做。

## 流程

### 1. 確認前置條件

- 修正已完成，相關測試已寫好且**全綠**
- 你知道「這個修正的哪一行是關鍵」——不是整個檔案，是那一行

若測試還沒綠，先讓它綠；反向驗證不是除錯手段。

### 2. 選出要退回的最小單位

退回**行為的關鍵那一行**，不是整包 revert。目標是模擬「這個 bug 還在」的狀態。

好的退回點：
- `const { valid } = await verify(...)` → `const valid = await verify(...)`（回到型別誤用）
- `epochTolerance: [30, 30]` → `[0, 0]`（回到無容差）
- `export const GET = withAdminAuth(async () => {` → `export async function GET() {`（回到無授權）

壞的退回點：
- 整個 `git stash`——會連測試一起退回，什麼都證明不了
- 刪掉整個函式——測試會因為 import 失敗而紅，那不是「抓到 bug」

**還原突變不要用 `git checkout -- <檔案>`。** 它還原的是整個檔案，會把你**同一個檔案裡
未 commit 的其他工作一起洗掉**——而反向驗證的時機正好都是「剛改完還沒 commit」。
還原方式一律二選一：(a) 用 Edit 把那幾行改回來（突變只有幾行，本來就改得回去）；
(b) 動手前先 `cp <檔案> <scratchpad>/<檔名>.bak`，用它當還原點。

### 3. 退回、跑測試、確認紅的是對的那條

```
Edit（退回關鍵行）→ 跑該測試檔 → 檢查輸出
```

**先確認突變真的發生了**，再看測試紅綠。突變後立刻 `git diff --stat <檔案>` 確認有增刪行數；
**若用腳本做突變，找不到目標字串時必須 `throw`／`exit(1)`，不可以靜默 no-op**。
2026-08-18 突變指令的引號被 shell 吃掉、檔案一個字沒變，測試理所當然全綠，
差點被當成「測試有鑑別力」——**沒有這一步，下面三件事全部是假的**。

**接著必須確認三件事**，缺一不算通過：

1. **有測試失敗**——全綠代表你的測試根本沒測到這個行為，回去重寫測試
2. **失敗的是你預期的那條**——不是因為 import 錯誤或型別錯誤而紅
3. **失敗訊息描述的是真實危害**——例如 `expected 200 to be 401` 說明「錯誤驗證碼會被放行」，
   而不只是 `undefined is not a function`

### 4. 改回並複跑

改回修正，再跑一次確認回到全綠。**不可以忘記這步**——留著退回狀態就是把 bug 送上線。

### 5. 在回報裡寫進證據

完成宣告要包含反向驗證的結果，不是只說「測試全過」：

> 已驗證：把 `.valid` 暫時退回舊寫法重跑，該測試如預期失敗
> （`expected 200 to be 401`——舊碼對錯誤驗證碼回 200 並發 session），再改回。

## 什麼時候該用

**一定要用**：
- 安全修正（auth、授權、XSS、注入、簽章驗證）
- 金流、庫存扣減相關的修正
- 「這個 bug 之前沒被任何測試抓到」的情況——代表測試有系統性盲區

**建議用**：
- 修正涉及外部套件的回傳值、單位、格式（型別誤用與單位錯誤特別容易自我一致）
- 加了新的驗證邏輯（長度、範圍、格式）

**不必用**：
- 純新增功能且無對應的「錯誤行為」可退回
- 文件、註解、設定值調整

## 常見錯誤

**斷言寫成「不包含某字串」**：驗轉義類修正時，`expect(html).not.toContain('<script>')`
是錯的判準——轉義後的內容本來就會保留那些**文字**。要驗結構：數開閉標籤個數、
取出屬性值後檢查沒有未轉義的界定符、解碼後與原輸入比對。
（詳見 lessons.md 歸檔區 2026-08-27 精簡那節；完整原文用 `git show 8bc2a4a^:.claude/playbooks/lessons.md` 取出）

**測試與程式碼共用同一個錯誤假設**：sanity-webhook 那次就是。
反向驗證能抓到大部分這類問題，但若連測試的前提都錯了，最可靠的是
**用另一種方式獨立算出期望值**（例如手算檢查碼、查官方文件的格式範例），
而不是拿自己實作的輸出當標準答案。
