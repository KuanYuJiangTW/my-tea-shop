# 判斷力外化：rubric 與 checklist（JUDG）

> 把「什麼時候該做什麼」寫成可執行判準。每條附正例與反例——正例是該觸發的情況，反例是不該觸發（誤用）的情況。
> 例子多取自本 repo（ECPay、庫存、2FA、i18n），可直接類比。

## JUDG-1 何時升級模型

**判準（任一成立就升級／直接從高階起跳）**：
- 失敗次數到達 dispatch.md DISP-5 門檻（haiku 敗 1 次、sonnet 同一子任務敗 2 次）
- 事前可判定的難題：要跨 3 個以上模組追因果，或要在互相衝突的目標間取捨（例如效能 vs 一致性）→ 直接 opus，不要「先省後浪費」
- 問題只有「為什麼會這樣」而沒有穩定重現步驟（開放式診斷）→ 最低 sonnet，不派 haiku

**正例**：ECPay 回調偶發驗簽失敗，無穩定重現，同時涉及時區與編碼兩個假設 → 開放式診斷＋跨模組 → 直接派 opus。
**反例**：「把 `messages/zh-TW.json` 裡 40 處『茶葉』改成『茶品』」→ pattern 完全明確的機械活 → haiku 就夠。升級是失敗處理機制，不是尊爵待遇；沒有失敗訊號就用貴模型＝浪費。

## JUDG-2 何時算真的完成

**定義：完成＝驗收條件逐條有證據＋獨立驗證通過＋已 push。**三者缺一都不是完成。

- 每條驗收條件有對應證據：測試輸出、實跑結果、或 checker 的 read-back 報告
- 改動範圍的**既有**測試也全綠（`npm run test`），不是只有新加的測試綠
- 已 push 且 `git log origin/<branch> -1` 確認遠端收到
- 完成宣告裡出現「應該可以」「理論上」「大概沒問題」→ 自動判定未完成

**正例**：修庫存扣減競態 → 證據三件：既有測試綠（貼輸出末段）、新增併發測試綠、checker 確認 RPC 有 row-level lock（引 file:line）→ 完成。
**反例**：改了 checkout 表單驗證，沒跑測試，理由是「改動很小應該沒問題」→ 未完成。**改動小不是證據，測試輸出才是。**

## JUDG-3 何時停下來問使用者

預設自主（問問題會把成本轉嫁給使用者），但**這五種必問**：
1. 破壞性且難回復：刪資料、動 production 設定、force push 共用分支、對外發送（email、公開 PR 留言）
2. 規格有兩種以上說得通的解讀，且選錯要重做 30 分鐘以上
3. 要動錢、憑證、第三方帳號（本 repo：Stripe/PayPal/ECPay/Supabase/Resend 的 key 與設定）
4. 驗收條件寫不出來——連「怎樣算對」都定不出來，這是需求問題，執行端解不了
5. 發現使用者的前提錯了（要求修 A，但 A 沒壞、壞的是 B）→ 回報發現並確認，不要默默改成做 B

**問法規定**：給 2–3 個選項＋你的推薦＋各自後果。禁止開放式的「你想要怎樣？」。

**正例**：「幫折價券加排除規則」——是不能與積分併用，還是不能與其他券疊用？兩種解讀都合理、資料表設計完全不同、改錯重做遠超 30 分鐘 → 問，附兩案與推薦。
**反例**：修一個 typo 還去問「是要改成 X 嗎？」——單一合理解讀、錯了 10 秒改回來 → 不問，直接做。**可逆的小事拿去問＝打擾。**

## JUDG-4 方向錯了的訊號（換路，不是重試）

**訊號（同時成立兩個以上 → 停止重試，回到診斷）**：
- 同一症狀，兩個**不同**修法都無效 → 你修的可能不是病灶
- 修一處、別處冒新錯，連鎖三次以上 → 動錯了抽象層
- fix 的 diff 越改越大、越來越繞，在跟框架打架 → 多半有官方正解沒找到
- 解釋 bug 需要「剛好」的巧合（時序剛好、cache 剛好）→ 假設太脆弱
- 答不出「那之前為什麼能動？」→ 還沒理解系統，先別改

**換路動作**：停止改 code → 把當前所有假設寫進 WORKLOG → 做最小重現逐一驗證假設 → 假設全滅就走 DISP-5 升級或 JUDG-3 問人。

**正例**：next-intl 路由 404，改 middleware matcher 無效、改 locale prefix 也無效 → 兩修法無效 → 停手寫最小重現 → 發現是 `src/proxy.ts` 攔了路徑，病灶根本不在 i18n。
**反例**：測試失敗，錯誤訊息明確指出 assertion 過時（功能改了、斷言沒跟上）→ 因果已知的直線修正，第一次失敗不是「方向錯」訊號 → 直接修。**訊號要的是「反覆無效」，不是「失敗過一次」。**

## JUDG-5 品質底線怎麼驗

**最低門檻（全過才能 commit）**：
1. `npm run test` 全綠；高風險區（金流、庫存、auth/2FA、RLS、cron）改動前先讀 `openspec/specs/` 對應規格
2. `npm run lint` 無**新增**錯誤（宣稱「錯誤是既有的」→ 要用 `git stash` 前後對比證明，不能用「應該是」）
3. diff 讀起來像周圍的 code：命名風格、註解密度一致；使用者可見字串進 `messages/`（zh-TW＋en 兩份），不硬編碼
4. 無殘留 debug：`console.log`、註解掉的舊碼、沒登記進 WORKLOG 的 TODO
5. 邊界條件至少想過這四個：空值／未登入／重複提交／zh 與 en 兩語系

**驗的方式**：以上自查完，仍要過 dispatch.md DISP-6 的獨立驗證（checker 或 `code-review` skill medium 以上）。**自查不取代獨立驗證**，它只是讓你少在 checker 面前丟臉。

**正例**：新增 API route → 測試綠＋lint 對比無新增＋錯誤處理寫法對照隔壁 route＋未登入回 401 驗過＋checker PASS → 進 commit。
**反例**：「lint 有 3 個錯，但看起來都是既有的」→ 沒對比就放行 → 違規。去跑對比，10 秒的事。

## 極限與代償（誠實條款——制度做不到的事）

**制度補得了**：執行紀律、驗證、成本控制、失敗處理。以下兩類**補不了**，遇到照寫的做：

1. **模糊需求與品味判斷**（UI 好不好看、文案語氣對不對、「感覺不對」）：
   checklist 驗不出品味，弱模型的品味判斷也不可靠。做法：
   - 產出 2–3 個變體，讓使用者選——把品味判斷還給人；
   - 使用者不在且非做不可 → `judge` 第二意見過濾明顯爛案，並在回報裡**明說**「這只保下限，不保品味」。
2. **新穎的架構決策**（沒有前例可對照的取捨）：
   多樣本評審能濾掉爛案，選不出「對這個生意最好」的案。做法：
   - 給使用者 2 案＋各自後果＋推薦＋信心標註；
   - 使用者不在 → 選**可逆性較高**的那案，決策理由寫進 WORKLOG 決策紀錄，下次使用者出現時主動回報。

**通用原則**：不確定就標「不確定＋缺什麼依據」。演出來的自信＝編造，是整套制度的頭號敵人。
